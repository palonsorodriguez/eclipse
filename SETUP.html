Agent workflow setup

This repository runs coding agents from GitHub Actions using Sandcastle. You drive the agents by applying labels to issues and pull requests — no local runtime, no Docker, no terminal. This page is the step-by-step install guide, from a fresh clone to a first agent-authored pull request.

How it works

Every agent task is a small TypeScript script under .sandcastle/ paired with a Markdown prompt. A GitHub Actions workflow checks out the repo, installs dependencies and the Claude Code CLI, then runs that script on the runner. Sandcastle handles invoking the agent, capturing its session, retrying structured output, and reporting the commits it produced.

Issue → label agent:implement → branch + commits → draft PR → label agent:review → inline review comments

The runner itself is the sandbox: the scripts use Sandcastle's noSandbox() provider because the ephemeral VM already gives the isolation. The Docker provider in .sandcastle/main.ts is only used for the optional local loop described at the end of this page.

Prerequisites

  • Node.js 22+ and npm, for the one-time local install.
  • Claude Code CLI on your machine, only to generate an auth token: npm install -g @anthropic-ai/claude-code.
  • A GitHub repository you own, with Issues and Actions enabled. Sub-issues and issue dependencies are used by the PRD and queue workflows.
  • An active Claude subscription (or an Anthropic API key — see step 3).
Cost warning. Every labelled issue starts a real agent run that consumes tokens, and the architecture-review workflow runs on a weekday schedule. Read step 8 before enabling anything on a repo you care about.

Installation

1

Install dependencies

From the repository root. This creates package-lock.json, which the workflows need — they run npm ci. 

npm install

Verify the agent scripts are healthy:

npm run typecheck
npm test

Both must pass. The second command runs Sandcastle's own unit tests for the retry, extraction, and diff-parsing helpers.

2

Push the repository to GitHub

git add .
git commit -m "chore: add sandcastle agent workflows"
git push origin main

Workflows only exist once they are on the default branch. Commit package-lock.json — without it npm ci fails on the runner.

3

Create the Claude auth secret

Generate a long-lived OAuth token from your Claude subscription:

claude setup-token

Copy the token, then in GitHub go to Settings → Secrets and variables → Actions → New repository secret and add:

Name Value
CLAUDE_CODE_OAUTH_TOKEN The token printed by claude setup-token
Using the API instead? Replace CLAUDE_CODE_OAUTH_TOKEN with ANTHROPIC_API_KEY in every workflow's env: block and in the claudeCode(...) calls under .sandcastle/. Billing then goes through the Anthropic API rather than your subscription.
4

Create AGENT_PAT (strongly recommended)

The built-in GITHUB_TOKEN has two limits that break the chain: it cannot push changes to files under .github/workflows/, and labels it applies do not trigger other workflows. That second one matters — without a PAT, agent-implement cannot hand off to agent-review.

Create a fine-grained personal access token at github.com/settings/personal-access-tokens, scoped to this repository only, with these repository permissions:

  • Contents — Read and write
  • Issues — Read and write
  • Pull requests — Read and write
  • Workflows — Read and write
  • Metadata — Read-only (mandatory)

Save it as the repository secret AGENT_PAT. Every workflow falls back to GITHUB_TOKEN if it is missing, so the setup still runs — you just have to re-apply hand-off labels manually.

5

Open up Actions permissions

Under Settings → Actions → General, in the Workflow permissions section:

  • Select Read and write permissions.
  • Tick Allow GitHub Actions to create and approve pull requests.

Without these, the agent produces commits but cannot open the pull request.

6

Create the labels

Go to Actions → Setup Labels → Run workflow. It reads .github/labels.json and creates every label the workflows depend on, with the exact names, descriptions and colours listed below. Re-running it updates existing labels in place and never deletes anything.

Label Colour Meaning
agent:implement #0E8A16 Trigger the agent-implement workflow
agent:review #0E8A16 Trigger the agent-review workflow on this PR
agent:to-issues #0E8A16 Trigger the agent-to-issues workflow
agent:update-branch #0E8A16 Trigger: merge base into this PR
agent:in-progress #FBCA04 An agent workflow is currently running on this issue/PR
agent:queued #FBCA04 Issue is queued for an agent workflow
agent:blocked #B60205 Agent run failed; re-add the trigger label to retry
source:architecture-review #5319E7 PRDs proposed by the automated architecture-review workflow

Prefer the command line? With the GitHub CLI installed and authenticated: 

jq -c '.[]' .github/labels.json | while read -r l; do
  gh label create "$(echo "$l" | jq -r .name)" \
    --color "$(echo "$l" | jq -r .color)" \
    --description "$(echo "$l" | jq -r .description)" --force
done
7

Fill in the project context

Agents read these before touching code. Empty placeholders produce generic, low-quality work — this step is the single biggest lever on output quality.

  • CONTEXT.md — what Eclipse is, its domain vocabulary, its architecture.
  • .sandcastle/CODING_STANDARDS.md — the rules reviewers enforce. Add project-specific rules as they emerge.
  • docs/adr/ — one file per settled architectural decision, so agents stop re-litigating them.
8

Decide what runs unattended

.github/workflows/architecture-review.yml is scheduled at 0 9 * * 1-5 — 09:00 UTC on weekdays. It inspects the codebase and opens PRD issues on its own. If you would rather trigger it by hand, delete the schedule: block and keep workflow_dispatch:.

Everything else is label-driven and only runs when you ask for it.

9

First run

  1. Open an issue with a clear title and a body that states the acceptance criteria. Write it as a specification, not a hint.
  2. Apply agent:implement.
  3. Watch Actions → Agent Implement. The label flips to agent:in-progress, and on success a draft pull request appears with agent:review already applied.
  4. If it fails, the issue gets agent:blocked plus a comment with the reason and a link to the run. Fix the cause and re-apply agent:implement to retry.

Workflow reference

Workflow Trigger What it does
agent-implement.yml agent:implement on a standalone issue Branches from main, implements the issue, writes the PR title and body, opens a draft PR, requests review.
agent-implement-prd.yml agent:implement on an issue that has sub-issues Treats the issue as a PRD and implements its sub-issues in sequence on a single branch.
agent-implement-pr.yml agent:implement on a pull request Reads the review comments on the PR and pushes commits that address them.
agent-review.yml agent:review on a PR Reviews the diff against CODING_STANDARDS.md and the originating issue, applies quality fixes as one squashed commit, and posts inline comments.
agent-to-issues-prd.yml agent:to-issues Splits a PRD issue into sub-issues using the project's vocabulary.
agent-update-branch.yml agent:update-branch on a PR Merges main into the PR branch and resolves conflicts.
agent-promote-queued.yml Any issue closing Finds agent:queued issues that listed it as a blocker and promotes the now-unblocked ones to agent:implement.
architecture-review.yml Weekday schedule / manual Audits the codebase and opens one PRD issue labelled source:architecture-review when the backlog is thin.
setup-labels.yml Manual Creates or updates every label from .github/labels.json.

Optional: the local loop

.sandcastle/main.ts is an autonomous loop that plans work from open issues, implements up to four in parallel Docker sandboxes, reviews each, and merges the branches. It is independent of the GitHub workflows and needs more setup:

  1. Install Docker Desktop and start it.
  2. Install the GitHub CLI and run gh auth login.
  3. Copy .sandcastle/.env.example to .sandcastle/.env and fill in CLAUDE_CODE_OAUTH_TOKEN and GH_TOKEN. That file is gitignored.
  4. Run npm run sandcastle.
This one runs unattended. It loops up to ten times, committing and merging as it goes. Start it on a branch you are willing to throw away.

Troubleshooting

The PR opened but no review ever started

AGENT_PAT is missing or lacks pull-request permission. Labels applied with GITHUB_TOKEN do not trigger downstream workflows. Add the PAT, or re-apply agent:review by hand.

Push rejected: "refusing to allow a token to create or update workflow"

The agent changed a file under .github/workflows/ and AGENT_PAT lacks the Workflows permission.

npm ci fails on the runner

package-lock.json is not committed, or it is out of sync with package.json. Run npm install locally and commit the result.

Nothing happens when I apply a label

Check the label name character for character — the workflows match exactly, and a label created by hand as agent-implement or Agent:Implement will never fire. Re-run Setup Labels to get the canonical set.

The issue was ignored with no comment

agent-implement.yml skips silently when the issue has sub-issues — agent-implement-prd.yml owns that case. It refuses outright, with a comment, when the issue is itself a sub-issue of another one; label the parent PRD instead.
